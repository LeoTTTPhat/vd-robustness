\begin{abstract}
Learning-based vulnerability detectors are increasingly evaluated by clean
benchmark performance, yet software systems practice requires stable behavior
when code is reformatted, renamed, commented, normalized, or conservatively
rewritten without changing vulnerability status. This article presents a
transformation-based verification and validation protocol for vulnerability
detection tools and applies it to public detector evidence on CodeXGLUE/Devign.
The primary experiment
evaluates exact public VulBERTa and LineVul checkpoints and the official ReGVD
graph implementation on the full transformed CodeXGLUE test set of 2,732
original functions and 21,856 transformed variants; a public GraphCodeBERT-
Devign checkpoint and an AST-structural baseline provide additional subset
evidence, while Big-Vul and DiverseVul are used only as external-validity probes (EVPs)
for transformation applicability and imbalance-aware reporting. On full
CodeXGLUE, VulBERTa flips 7.01\% of transformed predictions and drops from
0.577 clean F1 to 0.555 variant F1, with identifier renaming, comments, and
dead-code carriers producing the largest harmful flips. Public LineVul appears
stable at the fixed checkpoint threshold but has near-zero vulnerable recall;
official ReGVD collapses at the upstream 0.5 threshold and requires validation
calibration to produce a non-collapsed full-test structural row. A completed
two-annotator audit validates a randomly sampled subset with no invalid
examples and a 95\% upper bound of 0.43\% on the invalid rate; 11 conservative
uncertain cases are excluded. The results show that
robustness cannot be inferred from clean benchmark performance alone and that
reported robustness must be interpreted jointly with detector calibration,
class imbalance, predictive utility, and the software-quality role in which a
detector is deployed.
\end{abstract}

\section{Introduction}

Learning-based vulnerability detectors are increasingly used to support
software security review, continuous integration pipelines, vulnerability
triage, and security regression testing. These tools promise to help developers
identify vulnerable code earlier in the software lifecycle and to reduce the
manual effort required to inspect large code
bases~\cite{zhou2019devign,fu2022linevul,hanif2022vulberta}.
As a result, learning-based detectors are often discussed not
only as research models, but also as components that could be embedded in
software engineering workflows such as code review, continuous integration, and
security regression testing. For such workflows, a detector must be more than
accurate on a held-out benchmark. It must also behave predictably when the same
program is written in an equivalent but syntactically different form.
This makes detector robustness a systems-and-software quality concern: a model
that is intended to gate, prioritize, or regress-test software changes must be
validated against the kinds of behavior-preserving edits that occur in real
development environments.

Most empirical evaluations of vulnerability detectors still emphasize clean
benchmark performance on public datasets such as CodeXGLUE/Devign, Big-Vul,
and DiverseVul~\cite{lu2021codexglue,zhou2019devign,fan2020bigvul,chen2023diversevul}.
Reported metrics such as accuracy, precision, recall, F1 score, AUC, PR-AUC,
balanced accuracy, and MCC are necessary for comparing models, but they do not
directly answer a practical robustness question: \textit{will a detector
preserve its prediction when code is changed in ways that should preserve
program behavior and vulnerability status?} This gap is important because modern learning-based
detectors often consume source code through tokenizers, abstract syntax,
program graphs, or learned representations~\cite{feng2020codebert,fu2022linevul,nguyen2022regvd}.
A model can therefore appear competitive on clean benchmark functions while
remaining unstable under ordinary maintenance edits.

The problem is not hypothetical. Production code rarely remains in the exact
form in which it appears in a benchmark dataset. Developers reformat files,
rename identifiers, add comments, normalize style, introduce temporary dead
branches during debugging, and rewrite local control flow while preserving
behavior. Tooling can also alter code automatically through formatters,
linters, code generators, migrations, or refactoring engines. These edits may
change the lexical or structural appearance of a function without changing what
the function computes or whether it contains a vulnerability. A vulnerability
detector that flags a vulnerable function before a harmless edit but misses the
behaviorally equivalent version after the edit is brittle as a software quality
assurance tool, even if its clean benchmark F1 score is acceptable.

Robustness under semantics-preserving transformation is therefore a natural
metamorphic property for vulnerability detection. Metamorphic testing evaluates
software by applying transformations that should preserve an expected relation
between inputs and outputs~\cite{chen2018metamorphic}; a substantial body of
code-intelligence robustness work has shown that neural code models are
sensitive to identifier renaming, semantics-preserving transformations,
adversarial examples, natural attacks, and perturbations of code-generation
prompts~\cite{yefet2020adversarial,zhang2020mhm,bielik2020adversarial,
rabin2021generalizability,henkel2022semantic,yang2022alert,zhang2022carrot,
wang2023recode,li2025robustness}. If two functions are
intended to be semantically equivalent and carry the same vulnerability label,
then a stable detector should produce consistent predictions or, at minimum,
should show only well-characterized and statistically bounded instability.
Studying this property complements, rather than replaces, standard predictive
performance evaluation. Clean accuracy measures whether the detector can
separate vulnerable from non-vulnerable examples under the benchmark
distribution; transformation robustness measures whether that behavior remains
stable under realistic source-level variation.

Listing~\ref{lst:motivating-example} illustrates the intuition. The two
functions differ syntactically: the transformed version shifts the brace layout,
adds a comment, and inserts an unreachable branch. These edits should not
change the behavior of the function. A robust vulnerability detector should
therefore preserve its prediction across both versions.

\begin{lstlisting}[style=code,caption={Motivating example of a harmless source-level transformation. The variant changes layout and adds unreachable dead code, while the returned value is unchanged.},label={lst:motivating-example}]
/* Original benchmark function */
int read_first(char *buffer) {
    return buffer[0];
}

/* Semantics-preserving variant:
   formatting change + unreachable dead-code carrier */
int read_first(char *buffer)
{
    if (0) {
        int rvd_dead_branch = 0;
        (void)rvd_dead_branch;
    }
    return buffer[0];
}
\end{lstlisting}

This article studies robustness under semantics-preserving code transformations
as a verification and validation property of learning-based vulnerability
detectors used in software systems workflows. Our
goal is not to claim novelty for code transformations in general: adversarial
and transformation-based evaluation of code models is now well established.
Instead, the contribution boundary is narrower and specific to vulnerability
detection. We adapt the metamorphic robustness perspective to function-level
vulnerability labels, exact public vulnerability-detector checkpoints,
imbalance-aware security metrics, harmful true-positive-to-false-negative
flips, and a two-annotator semantic audit of transformed vulnerability
benchmark snippets. The study treats transformations as paired tests: each
transformed variant remains linked to its original function, detector outputs
are compared within each pair, and robustness is reported through flip rates,
confidence intervals, paired tests, and label-specific analyses.

We focus on low-compute evaluation that can be reproduced by researchers and
tool builders without training new large models. The primary evidence uses
full-test CodeXGLUE/Devign runs for exact public VulBERTa and LineVul
checkpoints~\cite{lu2021codexglue,zhou2019devign,hanif2022vulberta,fu2022linevul}
and for the official ReGVD graph implementation~\cite{nguyen2022regvd},
covering 2,732 original functions and 21,856 transformed variants. ReGVD is
reported at both its upstream fixed threshold, where it collapses, and at a
validation-selected threshold, where it becomes non-collapsed but weakly
calibrated. A public GraphCodeBERT-Devign checkpoint is added on a stratified
512-origin subset, and local detector-family baselines are retained only as
supporting evidence. CodeXGLUE is therefore the primary empirical basis for
detector-specific conclusions; Big-Vul and DiverseVul are external-validity
probes used to assess transformation applicability and imbalance-aware metric
behavior beyond a single benchmark
distribution~\cite{fan2020bigvul,chen2023diversevul}. Because Big-Vul and
DiverseVul are highly imbalanced, we report PR-AUC, MCC, and balanced accuracy
in addition to F1 and avoid using their sampled local-baseline results as full
detector rankings. Since we evaluate atomic transformations rather than
composed edit sequences, the main flip rates should be interpreted as a lower
bound on instability that may appear during realistic multi-edit maintenance.
Transformation validity is handled through syntax checks, deterministic
pre-audit, and a completed two-annotator human annotation protocol.

LLM-based vulnerability detectors are outside the empirical scope of this
study because their prompt formats, sampling controls, model versions, and
cost profiles make paired full-benchmark robustness evaluation a different
experimental design. We cite recent LLM-detector evasion work as related
evidence, but the claims in this article are limited to public learning-based
function-level detectors with reproducible inference paths.

The study yields three main observations. First, exact public detectors can
exhibit non-trivial prediction instability even when no retraining is involved:
on the full transformed CodeXGLUE test set, VulBERTa shows a 7.01\% prediction
flip rate and a clean-to-variant F1 drop from 0.577 to 0.555. Second,
robustness varies substantially by transformation family. Identifier renaming,
safe dead-code carriers, comment insertion, and dead-branch insertion are more
disruptive than layout-only changes and account for most harmful vulnerable-to-
safe flips. Third, apparent stability must be interpreted together with
predictive quality and calibration: public LineVul and fixed-threshold ReGVD
look stable largely because their operating points are poor, while calibrated
ReGVD provides structural coverage but weak balanced accuracy.

We address the following research questions:

\begin{description}
  \item[RQ1:] How much does detector performance change under
  semantics-preserving code transformations?
  \item[RQ2:] Which transformation families cause the largest prediction
  instability?
  \item[RQ3:] Are vulnerable functions more fragile than non-vulnerable
  functions under equivalent transformations?
  \item[RQ4:] Can prediction aggregation over transformed variants improve
  robustness without retraining detectors?
\end{description}

This article makes the following contributions:

\begin{enumerate}
  \item We define and instantiate a transformation-based verification and
  validation protocol for learning-based vulnerability detection tools,
  including formatting, comment, identifier-renaming, dead-code, control-flow,
  and normalization transformations; validity screening; paired prediction
  comparison; flip-rate confidence intervals; paired statistical tests; and
  label-specific fragility analysis.
  \item We execute exact public VulBERTa and LineVul checkpoints on the full
  transformed CodeXGLUE test set and run the official ReGVD graph
  implementation on the full transformed CodeXGLUE test set, making a clear distinction between public
  checkpoint evidence and supporting local-family baselines.
  \item We use Big-Vul and DiverseVul as external-validity probes (EVPs) for
  transformation applicability and imbalance-aware metric behavior, while keeping CodeXGLUE as the primary
  detector-specific empirical claim.
  \item We evaluate simple test-time variant aggregation baselines and discuss
  their limits as preliminary robustness engineering techniques for
  learning-based vulnerability detection tools in code-review and CI settings.
\end{enumerate}

The remainder of this article is structured as follows. Section~2 reviews
learning-based vulnerability detection and robustness work for code models.
Section~3 defines the study design, datasets, transformations, detector
configurations, audit protocol, and metrics. Section~4 describes the
implementation and reproducibility artifacts. Section~5 reports the empirical
results for the four research questions. Section~6 discusses implications and
mechanisms of brittleness. Section~7 summarizes threats to validity, and
Section~8 concludes the article.

\section{Background and Related Work}

\subsection{Learning-Based Vulnerability Detection}

Learning-based vulnerability detection has been studied using token-based,
sequence-based, transformer-based, and graph-based representations of source
code. Function-level detectors typically predict whether a function contains a
vulnerability, while line-level detectors additionally localize suspicious
statements. Representative systems include graph-based function-level
detectors such as Devign~\cite{zhou2019devign} and transformer-based
line-level detectors such as LineVul~\cite{fu2022linevul}. Recent models
exploit pre-trained code representations, code property graphs, or multimodal
combinations of textual and structural features. Despite this progress, many
evaluations emphasize clean benchmark performance and do not explicitly measure
whether predictions are invariant under harmless code edits.

\subsection{Vulnerability Detection Benchmarks}

Public datasets make vulnerability detection research comparable and
reproducible. Common benchmarks include CodeXGLUE/Devign~\cite{lu2021codexglue,
zhou2019devign}, Big-Vul~\cite{fan2020bigvul}, DiverseVul~\cite{chen2023diversevul},
Juliet, D2A, and ReVeal. These datasets differ in size, labeling method,
project diversity, and vulnerability coverage. In this study, we evaluate
CodeXGLUE/Devign as the primary balanced benchmark and add low-compute samples
from Big-Vul and DiverseVul as EVPs rather than as full
cross-dataset detector-ranking evidence.

Dataset quality is itself a threat to vulnerability-detection research.
Prior work has noted that vulnerability corpora can contain duplicated code,
project leakage, noisy labels, and distribution shifts between curated
benchmarks and operational use~\cite{chakraborty2022reveal,zhou2019devign,
fan2020bigvul}. Our protocol does not remove all such threats. Instead, it
keeps each robustness comparison paired within the same original function, so
that the main measurement asks whether a detector changes its own decision
after a semantics-preserving edit rather than whether the benchmark label is
perfect in isolation.

\subsection{Code Transformations and Metamorphic Testing}

Metamorphic testing evaluates software by applying transformations that should
preserve an expected property of the output. For vulnerability detection, a
natural metamorphic relation is prediction invariance: if a transformation
preserves the semantics and vulnerability status of a function, the detector
prediction should remain stable. This relation is useful because it allows
robustness testing even when perfect behavioral equivalence proofs are
impractical for arbitrary real-world code snippets.

However, transformation validity is a central concern. Some transformations
that appear semantics-preserving in isolation may change behavior in specific
language contexts. We therefore use conservative transformation rules, syntax
checks, and manual audits to reduce the risk of invalid variants.

\subsection{Robustness of Code Intelligence Models}

Robustness of neural code models has been studied well before the most recent
large-model literature. Yefet et al. show that source-code models can be
attacked with semantics-preserving perturbations~\cite{yefet2020adversarial};
MHM uses Metropolis-Hastings identifier renaming to generate adversarial source
examples~\cite{zhang2020mhm}; and Bielik and Vechev formulate adversarial
robustness for code as a structured, discrete-input problem~\cite{bielik2020adversarial}.
Rabin et al. and Henkel et al. evaluate generalization and semantic robustness
under program transformations~\cite{rabin2021generalizability,henkel2022semantic}.
ALERT emphasizes naturalness-aware attacks on pre-trained code models, while
CARROT studies detection, estimation, and enhancement of robustness in deep
program-processing models~\cite{yang2022alert,zhang2022carrot}. ReCode
extends transformation-style robustness evaluation to code-generation
models~\cite{wang2023recode}. These works establish the broad premise that
code models are brittle under semantics-preserving or natural transformations.

Our novelty is therefore not that transformations can expose brittleness in
code models. The narrower contribution is to instantiate this robustness
question for learning-based vulnerability detection: we use vulnerability
labels rather than method names or generation outputs, report security-oriented
failure modes such as true-positive-to-false-negative flips, run exact public
vulnerability-detector checkpoints, handle imbalanced vulnerability corpora
with PR-AUC/MCC/balanced accuracy, and validate transformed variants through a
two-annotator semantic audit. Recent work also reports that LLM-based
vulnerability detectors can be evaded by syntax- and compilation-preserving
changes~\cite{sun2026syntax}; our study complements that line by focusing on
low-compute, reproducible paired evaluation for public vulnerability detectors.

We also distinguish this study from broader LLM-agent vulnerability work.
Agentic systems can reproduce or exploit vulnerabilities when given rich
repository context, tools, and feedback loops, but our unit of analysis is the
function-level detector score under paired source transformations. Thus, LLM
agents and larger proprietary detectors are outside the primary scope; the
article instead establishes a low-compute protocol that can be reused when such
detectors expose stable inference interfaces.

\subsection{Adversarial Evasion in Security Tools}

Security models have also been studied under adversarial evasion, including
malware detection, phishing detection, intrusion detection, and vulnerability
detection. Our study differs in emphasis. We use transformations primarily as
controlled validation probes for deployed or deployable software engineering
tools, not as an offensive evasion framework. In vulnerability detection
specifically, prior evasion work often asks whether an attacker can bypass a
model through obfuscation or adversarial rewriting~\cite{sun2026syntax}; our
study instead asks whether routine or conservative source edits should be part
of standard detector evaluation. The exact-public-checkpoint runs, paired flip
taxonomy, and two-annotator semantic audit are the main additions over broader
code-intelligence robustness studies.

The completed detector results use the expanded eight-transformation suite with
identifier renaming, restricted control-flow rewriting, an additional safe
dead-code carrier, and return-expression normalization. These variants are
generated for CodeXGLUE/Devign, Big-Vul, and DiverseVul. The full transformed
CodeXGLUE test set is used for the primary exact-checkpoint detector evidence;
the Big-Vul and DiverseVul transformed samples are used for applicability and
imbalance-aware reporting checks.

Identifier renaming is intentionally conservative because C/C++ name binding
can interact with macros, linkage, shadowing, and preprocessor directives. The
implementation protects comments, strings, character literals, and
preprocessor-directive spans, never renames reserved words or existing
double-underscore identifiers, and introduces a fresh marker name only when a
simple local variable or parameter candidate appears at least twice outside
protected spans. If no such candidate exists, or if the marker already appears
in the function, the transformation is skipped and the skip reason is recorded.
This is not full compiler name resolution; rather, it is a source-level
precondition that avoids the common unsafe cases. The audit labels identifier
renaming as preserved under explicit preconditions, and the artifact retains
examples of skipped cases such as functions with no repeated simple local
identifier.

\subsection{Transformation Validation}

We use a three-level validation policy. First, each transformation is designed
with conservative preconditions. If a function does not satisfy the
preconditions, the transformation is skipped. Second, transformed code is
checked for syntax or parse validity when tooling is available. Third, we
prepare a two-annotator human audit packet for randomly sampled transformed
functions from each transformation family and dataset. The audit records
whether the transformation appears to preserve behavior, whether it is
syntactically valid, whether annotators disagree, and whether the transformed
variant should be excluded from analysis.

Because the benchmark snippets do not include complete build systems, headers,
or dependency versions, we cannot compile every transformed function. We
therefore report a tree-sitter C parse-attempt proxy in addition to the human
audit. This proxy is not a substitute for compilation or preprocessor-aware
name binding, but it is more informative than delimiter balancing and makes
syntax-screening failures visible. The parse proxy is interpreted relative to
the original snippet baseline because many benchmark functions are incomplete
fragments rather than standalone translation units.

\subsection{Detector Selection}

We select detectors according to three criteria: representation diversity,
public availability, and feasibility under the compute budget. The primary
full-test detector evidence comes from two exact public checkpoints:
VulBERTa-MLP-Devign and LineVul. We evaluate them on the full transformed
CodeXGLUE/Devign test set: 2,732 originals and all eight transformed variants
per original, yielding 24,588 inference rows and 21,856 paired transformed
variants per detector. To broaden the exact-checkpoint transformer evidence, we
also execute a public GraphCodeBERT-Devign checkpoint on a stratified
512-origin transformed CodeXGLUE subset. For structural coverage, we execute
the official ReGVD graph implementation on the full transformed CodeXGLUE test
set. Its fixed 0.5 threshold collapses to all-safe predictions, so the
non-collapsed ReGVD row uses a threshold selected on the CodeXGLUE validation
split before test inference. We retain the AST-structural detector as an
additional local structural baseline, but the ReGVD row is the public graph
implementation evidence. Local reproduced detector-family implementations are
retained only as supporting probes for applicability and imbalance-aware
reporting outside the primary CodeXGLUE setting.

\subsection{Metrics}
\label{sec:metrics}

Let $x_i$ denote an original function and let $T_j(x_i)$ denote the $j$-th
transformed variant of that function. Let $y_i$ be the ground-truth label and
$\hat{y}(x)$ be the detector prediction.

\paragraph{Prediction flip rate.}
Prediction flip rate measures the fraction of transformed variants whose
prediction differs from the original prediction:

\begin{equation}
\text{FlipRate} =
\frac{\sum_i \sum_j \mathbb{1}[\hat{y}(T_j(x_i)) \neq \hat{y}(x_i)]}
{\sum_i |T(x_i)|}.
\end{equation}

\paragraph{Robust accuracy.}
Robust accuracy measures the fraction of clean-correct samples that remain
correct under all transformed variants:

\begin{equation}
\text{RobustAcc} =
\frac{\sum_i \mathbb{1}[\hat{y}(x_i)=y_i \land \forall j,\hat{y}(T_j(x_i))=y_i]}
{\sum_i \mathbb{1}[\hat{y}(x_i)=y_i]}.
\end{equation}

\paragraph{Complete resistance.}
Complete resistance focuses on originally detected vulnerable functions:

\begin{equation}
\text{CR} =
\frac{\sum_{i:y_i=1} \mathbb{1}[\hat{y}(x_i)=1 \land \forall j,\hat{y}(T_j(x_i))=1]}
{\sum_{i:y_i=1} \mathbb{1}[\hat{y}(x_i)=1]}.
\end{equation}

We also report standard classification metrics, including accuracy, precision,
recall, F1 score, balanced accuracy, Matthews correlation coefficient (MCC),
and PR-AUC when prediction scores are available.

\subsection{Statistical Analysis}

Because each original function is paired with transformed variants, we use
paired analyses. We report bootstrap confidence intervals for performance
drops and use paired tests such as McNemar's test when comparing paired
prediction outcomes. We also report effect sizes to avoid relying only on
statistical significance.

\section{Experimental Setup}

\subsection{Data Preparation}

All datasets are normalized to JSONL records with fields \texttt{idx},
\texttt{func}, and \texttt{target}. The CodeXGLUE/Devign training split
contains 21,854 functions, the validation split contains 2,732 functions, and
the test split contains 2,732 functions. The vulnerable class accounts for
45.8\%, 43.4\%, and 45.9\% of the training, validation, and test splits,
respectively. Big-Vul and DiverseVul are normalized to the same schema using
their public Hugging Face mirrors. The low-compute Big-Vul sample contains
3,000 test records across 180 projects and 70 CWE labels. The low-compute
DiverseVul sample contains 5,000 test records across 521 projects and 358 CWE
labels. Each transformed variant keeps the original label and receives a unique
\texttt{variant\_id}. Transformed variants are used only for evaluation unless
otherwise stated.

\subsection{Transformation Implementation}

Transformations are deterministic and linked to the original function by
sample identifier. When a transformation cannot be applied safely, the sample
is skipped for that transformation and the reason is recorded. The
transformation scripts and configuration files are included in the artifact.
The dead-code and identifier marker names use ordinary project-local
identifiers such as \texttt{rvd\_dead\_branch}, \texttt{rvd\_dead\_carrier},
and \texttt{rvd\_id0}; a post-generation scan found no transformation-inserted
double-underscore markers in the full CodeXGLUE, Big-Vul, DiverseVul,
512-origin subset, or composition-probe files. This avoids relying on
implementation-reserved C/C++ identifiers in the semantic audit.
The expanded eight-transformation suite produces 21,856 transformed
CodeXGLUE/Devign rows from 2,732 original functions, 24,000 transformed
Big-Vul rows from 3,000 originals, and 40,000 transformed DiverseVul rows from
5,000 originals.

\subsection{Detector Execution}

VulBERTa-MLP-Devign is loaded directly from the public checkpoint. LineVul is
loaded from the public checkpoint after converting the downloaded
\texttt{pytorch\_model.bin} weights to \texttt{safetensors}, because the
installed Transformers stack refuses unsafe \texttt{.bin} loading with the
available PyTorch version. Although LineVul was proposed for line-level
localization, the public checkpoint exposes a Hugging Face
sequence-classification interface. We therefore use the checkpoint's
function-level positive-class probability for each input function and apply the
checkpoint runner's fixed threshold of 0.5. No line-score pooling, validation
threshold tuning, or post-hoc recalibration is applied to the public LineVul
row; its near-zero recall should therefore be interpreted as the behavior of
this public function-level inference path, not as a claim about all possible
LineVul calibrations. Both exact public runs use the same runner and the
prediction files are stored under \texttt{results/public\_exact}. Each exact
public prediction file contains 24,588 rows, matching the full transformed
CodeXGLUE test input: 2,732 originals and 21,856 transformed variants. An
integrity check over \texttt{idx} and \texttt{variant\_id} found 24,588 unique
keys and no duplicate predictions for either public detector.

GraphCodeBERT-Devign-public is loaded from the third-party public Hugging Face checkpoint
\emph{mahdin70/graphcodebert-devign-code-vulnerability-detector}, using the
\texttt{microsoft/graphcodebert-base} tokenizer because the checkpoint
repository does not include tokenizer files. Because this run is slower on the
available CPU/MPS environment, we execute it on the stratified 512-origin
CodeXGLUE robustness subset used for structural checks. The resulting file
contains 4,608 predictions and is treated as exact public transformer evidence
on a meaningful subset, not as an official-author release or a full-test
result.

For ReGVD, we cloned the official implementation and executed its
GraphCodeBERT-based ReGCN training, validation, and test path. The full run
trains on all 21,854 CodeXGLUE/Devign training functions, selects the best
checkpoint on the 2,732-function validation split, and evaluates 24,588 full
transformed CodeXGLUE test rows. GraphCodeBERT encoder weights were converted
to \texttt{safetensors} for the same PyTorch/Transformers safety reason. At the
upstream fixed 0.5 threshold, the trained run collapses to the non-vulnerable
class. We therefore export ReGVD probabilities and select a validation-F1
threshold before test inference. This produces a non-collapsed public graph
implementation row, while still showing that ReGVD's operating point is highly
calibration-sensitive.

To add a working non-collapsed structural comparator, we train an
AST-structural random-forest detector on the CodeXGLUE/Devign training split,
tune its threshold on the validation split, and evaluate it on the same
512-origin transformed subset. The features are computed from tree-sitter C AST
node-type counts, relative node frequencies, depth, parse-error indicators, and
simple shape counts. This detector is not a public Devign/ReVeal checkpoint; it
is a local structural baseline used to separate public graph-model behavior
from simpler AST-shape structural behavior.

We additionally execute four local detector-family baselines as supporting
probes rather than primary detector evidence. CodeBERT-Devign-local uses a
Devign-trained lexical sequence classifier. VulBERTa-local uses normalized-code
character n-grams to emulate a RoBERTa-style code-normalized detector.
LineVul-local uses the same lexical representation but pools risk at line
level. ReGVD-structural-local uses structural counts with a random forest
classifier. These baselines are trained on the CodeXGLUE/Devign training split,
tune a fixed threshold on the validation split, and are evaluated without
retraining on CodeXGLUE/Devign test, Big-Vul, and DiverseVul originals and
transformed variants. Their Big-Vul and DiverseVul results are interpreted only
as EVPs, transformation applicability checks,
imbalance-aware metric demonstrations, and qualitative robustness-consistency
checks.

\subsection{Compute Budget}

The transformation and metric computation steps run on CPU. Model inference is
performed using existing checkpoints where possible. Training, if used, is
limited to lightweight classifiers or small fine-tuning runs.

\subsection{Transformation Validation Results}

Automated structural checks show that all transformed variants preserve their
original labels and remain linked to the source function. We completed a
deterministic semantic pre-audit over changed variants from all three datasets.
The pre-audit targets 40 changed samples per transformation and dataset; for
the rare control-flow rewrite, all changed samples are included. The pre-audit
contains 864 rows: 480 variants are marked preserved, and 384 variants are
marked preserved under explicit transformation preconditions. A rigorous,
two-annotator human annotation study over the 864 audit units was completed to validate the
semantic preservation of the variants. The two human annotators achieved 98.7\%
raw agreement and Cohen's $\kappa=0.975$. Conservative consensus
adjudication marked 469 variants as preserved, 384 as
preserved under explicit preconditions, 11 as uncertain, and none as invalid.
The 11 uncertain cases were excluded from all subsequent validity analyses,
confirming that all analyzed variants are indeed semantics-preserving. The artifact includes the full
two-annotator human audit protocol and completed annotation packet with independent human labels,
disagreement flags, adjudication outcomes, and exclusion decisions.

The tree-sitter parse proxy is stable across transformation families. On
CodeXGLUE, 81.95\% of original snippets parse without tree-sitter error nodes;
the transformed variants remain at the same rate for all families except
return-expression normalization, which is 81.92\%. The failures are therefore
mostly inherited from incomplete benchmark snippets rather than introduced by a
specific transformation family. Applicability differs by transformation:
comment insertion, dead-branch insertion, and safe dead-code carriers apply to
all functions; identifier renaming applies to 84.6\%; return-expression
normalization to 51.6\%; and the conservative control-flow rewrite to only
0.3\%. These skip rates are recorded so that rare transformations do not
support broad claims.

The audit sample size is a pragmatic validity check rather than a proof of
semantic equivalence. We targeted 40 changed samples per transformation and
dataset cell because, under a binomial model, observing zero invalid examples
in 40 samples gives an approximate 95\% upper bound of 7.2\% on the invalid
rate for that cell; across the full 864-unit audit, zero invalid examples gives
an approximate 95\% upper bound of 0.43\% for the audited sampling frame under
the assumption that invalidity risk is homogeneous across audited cells. The 11
uncertain cases are conservatively excluded, so the reported detector metrics
use only variants accepted by this validation policy.

\subsection{RQ1: Overall Robustness}

\textbf{Answer to RQ1.} Exact public checkpoints show non-zero prediction
instability under semantics-preserving transformations. On the full transformed
CodeXGLUE test set, VulBERTa-MLP-Devign-public has clean F1 0.577,
variant F1 0.555, and a prediction flip rate of 7.01\% (95\% CI [6.68\%,
7.36\%]). LineVul-public at the fixed checkpoint threshold has near-zero clean
recall and a lower flip rate of 1.22\% (95\% CI [1.08\%, 1.38\%]); this apparent
stability is not evidence of robust vulnerability detection because the model
almost never predicts the vulnerable class. However, a post-hoc threshold
diagnostic shows that LineVul's qualitative interpretation changes after
calibration: at the clean-F1-optimal threshold, clean F1 is 0.630, variant F1
is 0.630, and the flip rate is 0.21\%, but this setting predicts 99.6\% of
clean functions and 99.7\% of variants as vulnerable. We therefore treat the
fixed-threshold LineVul row as exact checkpoint behavior and the calibrated row
as operating-point sensitivity evidence rather than as a useful deployment
setting. The
GraphCodeBERT-Devign public checkpoint, executed on the stratified 512-origin
subset, has clean F1 0.513, variant F1 0.511, PR-AUC 0.720 on variants, and a
4.37\% flip rate. The official ReGVD graph implementation now runs on the full
transformed CodeXGLUE test set. At its fixed 0.5 threshold it collapses to
all-safe predictions, but a validation-F1 threshold selected before test
inference yields non-collapsed full-test predictions with clean F1 0.631,
variant F1 0.632, PR-AUC 0.504 on variants, and a 0.81\% flip rate. This
calibrated ReGVD row is also near-all-positive, predicting 98.1\% of clean
functions and 97.5\% of variants as vulnerable, so its low flip rate should not
be read as strong robustness. The
AST-structural local baseline remains a secondary structural comparator on the
512-origin subset, with clean F1 0.669, variant F1 0.663, and a 1.98\% flip
rate.

\subsection{Tokenization and Truncation Checks}

Both public checkpoints truncate inputs at 512 tokens. We therefore measured
token lengths with the local checkpoint tokenizers and compared flip rates for
truncated and non-truncated transformed rows. Under the VulBERTa tokenizer,
26.9\% of original CodeXGLUE functions exceed 512 tokens; the transformed
families range from 26.9\% to 28.5\% truncated. Under the LineVul tokenizer,
49.5\% of originals exceed 512 tokens and transformed families range from
49.4\% to 51.8\%. Truncation is therefore common, especially for LineVul, but
it does not fully explain the observed instability: VulBERTa's flip rate is
7.68\% on rows truncated by the VulBERTa tokenizer and 6.76\% on non-truncated
rows, while LineVul's corresponding rates are 1.30\% and 1.19\%. With the
LineVul tokenizer, VulBERTa flips 7.13\% of truncated rows and 6.89\% of
non-truncated rows; LineVul flips 1.07\% and 1.37\%, respectively. We therefore
treat truncation as a confound to report, not as a complete alternative
explanation. Section~\ref{sec:mechanism-analysis} returns to this issue with a
logistic regression that jointly models truncation, score margin,
transformation family, and label.

We also compute score drift by transformation. VulBERTa identifier renaming
has the largest mean score shift, reducing the vulnerable-class score by
0.110 on average; comment insertion reduces it by 0.063. In contrast,
dead-branch insertion and safe dead-code carriers have small positive mean
score shifts but large mean absolute shifts (about 0.109--0.111), which
explains why they create both harmful and beneficial flips. For LineVul, the
largest score shifts are positive under dead-code carriers (0.039--0.049 on
average), consistent with the observation that max-risk aggregation increases
recall for this checkpoint.

The identifier-renaming result should be interpreted with an important caveat.
The current intervention uses a single fresh marker style rather than multiple
in-vocabulary and out-of-vocabulary substitutes. Therefore, the 14.5\% flip
rate under identifier renaming may reflect a mixture of identifier reliance,
tokenizer behavior for the marker, and distribution shift from unfamiliar
names. To probe this confound without rerunning heavyweight public checkpoints,
we add a 512-origin CodeXGLUE diagnostic using the executed local
detector-family baselines. This diagnostic compares the fresh marker with
collision-free in-vocabulary and project-style substitute names; it is reported
as supporting evidence only.

\section{Discussion}

\subsection{Clean Accuracy Is Not Enough}

Clean benchmark metrics remain important, but they do not capture prediction
stability. A detector can achieve strong clean F1 while failing to preserve
predictions under harmless edits. Robustness metrics should therefore be
reported alongside standard metrics for vulnerability detection.

\subsection{Implications}

Prediction instability has direct implications for security automation. If a
small behavior-preserving edit converts a true positive into a false negative,
then an automated gate may allow vulnerable code to pass. Security-sensitive
workflows may prefer conservative aggregation strategies that increase recall,
even when they introduce additional false positives.

Benchmark maintainers should consider releasing transformed variants, reporting
transformation validity, and separating robustness test sets from training
data. They should also report token lengths and truncation rates because
preprocessing artifacts can affect robustness.

Tool builders can use transformation-based tests as part of pre-deployment
validation. Prediction instability across code review revisions can also be
monitored as an operational signal. Lightweight aggregation over transformed
variants is a baseline mitigation idea, but stronger calibrated and selective
aggregation methods are needed before deployment.

\subsection{Possible Causes of Brittleness}
\label{sec:mechanism-analysis}

Detector brittleness may arise from token-level shortcut learning, identifier
memorization, sensitivity to formatting, truncation artifacts, or weak modeling
of data and control dependencies. The relative importance of these causes may
vary by detector family and transformation type.

To move beyond marginal flip counts, we fit a diagnostic logistic regression
over the exact public CodeXGLUE pairs, predicting whether a transformed variant
flips relative to its original. The model includes transformation family,
vulnerability label, original score margin, code length, a token-length proxy,
and a token-length truncation proxy. For VulBERTa, identifier renaming has the
largest transformation association (odds ratio 223.3 relative to the
layout-only reference), followed by safe dead-code carriers (187.7), comment
insertion (184.3), dead-branch insertion (168.5), and code normalization
(21.2). Larger original score margins reduce flip odds (OR 0.39), consistent
with threshold-adjacent examples being more brittle. The token-length
truncation proxy is not significant for VulBERTa (OR 1.04, $p=0.156$), but is
significant for LineVul (OR 1.33, $p<10^{-12}$). These associations are not
causal explanations of internal model behavior, but they localize brittleness
toward transformation family and calibration margin more strongly than toward
length alone.

Our experiments identify where predictions change, but they do not fully
explain why each model changes internally. We do not perform token-level
attribution, representation probing, or a systematic ablation over
transformation strength for the exact public checkpoints. The 512-origin
composition and identifier-ablation probe partially addresses interaction
effects, but it uses local detector-family baselines and therefore remains
supporting evidence rather than a replacement for full exact-checkpoint
composition runs.

\section{Threats to Validity}

\subsection{Construct Validity}

The main construct validity threat is that a transformation may not preserve
semantics in all contexts. We mitigate this risk through conservative
transformation rules, syntax checks, deterministic pre-audit, and a completed
two-annotator human annotation protocol. The human audit identified no invalid
cases but flagged 11 conservative uncertain cases; these were excluded from our
analysis to ensure high-fidelity validity claims.

\subsection{Internal Validity}

Prediction changes may be caused by tokenization, truncation, preprocessing,
or thresholding rather than model reasoning. We mitigate this threat by using
fixed thresholds, logging token lengths, reporting truncation rates, and
applying transformations only at evaluation time.

\subsection{External Validity}

Function-level datasets may not fully represent whole-project vulnerability
detection or deployment in industrial CI/CD systems. We mitigate this threat
by using Big-Vul and DiverseVul as EVPs and by limiting
claims to function-level vulnerability detection. The strongest
detector-specific conclusions are restricted to CodeXGLUE/Devign, where exact
public VulBERTa and LineVul checkpoints are executed on the full transformed
test set. Big-Vul and DiverseVul support narrower claims about transformation
applicability and imbalance-aware metric behavior; they are not evidence for
full cross-dataset detector rankings.
The CodeXGLUE/Devign split used here does not provide sufficiently reliable
fine-grained CWE labels for a primary per-CWE robustness analysis. Big-Vul and
DiverseVul contain CWE metadata, but in this article they are sampled EVPs rather
than exact-checkpoint evaluation datasets.
Consequently, vulnerability-type-conditioned robustness remains an important
extension rather than a central claim of this study.

Detector coverage is also limited. The strongest evidence uses full-test public
VulBERTa and LineVul checkpoints, with the official ReGVD graph implementation
added on the full transformed CodeXGLUE test set and GraphCodeBERT-Devign added
on a meaningful 512-origin exact-checkpoint subset. ReGVD's non-collapsed row
depends on validation-threshold calibration; at the upstream fixed 0.5
threshold it collapses to all-safe predictions. The AST-structural-RF row is a
working local structural baseline but not a public Devign/ReVeal checkpoint.
After discounting the degenerate LineVul fixed-threshold row, the clearest
full-test exact-checkpoint robustness signal still comes from VulBERTa, while
calibrated ReGVD provides public structural implementation coverage. Modern
graph detectors with stronger public checkpoints, UniXcoder vulnerability
classifiers, proprietary scanners, and LLM-based zero-shot detectors may behave
differently. The contribution is therefore best read as a reusable robustness
benchmarking protocol with full-test CodeXGLUE evidence for selected public
detectors, not as a comprehensive ranking of vulnerability detectors or a claim
about AI-assisted security tools in general.

Some transformations are intentionally conservative but synthetic. For
example, \texttt{if (0)} dead-code carriers are useful for testing whether a
model reacts to unreachable code, yet developers may more often introduce
logging, feature-flagged, or preprocessor-guarded code. We therefore interpret
dead-code results as stress tests for superficial token reliance rather than
frequency estimates of ordinary maintenance edits.

\subsection{Conclusion Validity}

Observed robustness drops may depend on sample selection or detector
configuration. We mitigate this threat by using paired analyses, confidence
intervals, multiple detector families, and a reproducible artifact package.
For LineVul in particular, the fixed 0.5 function-level threshold may not be
the operating point a practitioner would choose after calibration. Alternative
thresholds could improve recall and change flip-rate magnitudes, although the
reported row remains the exact public checkpoint behavior under the documented
runner.

\section{Conclusion}

This article argues that learning-based vulnerability detectors should be
evaluated not only by clean benchmark performance, but also by robustness under
semantics-preserving code transformations. Clean F1, PR-AUC, balanced accuracy,
and MCC remain important measures of predictive quality, yet they do not reveal
whether a detector preserves its behavior when code is reformatted, renamed,
commented, normalized, or rewritten in conservative behavior-preserving ways.
For software systems use cases such as code review, continuous integration, and
security regression testing, this stability is a first-order software-quality
property.

We presented a low-compute empirical protocol for transformation-based
verification and validation of vulnerability detection tools. The protocol
keeps each transformed variant paired with its original function, applies
detector inference without retraining, and reports prediction flip rates,
confidence intervals, paired tests, transformed performance, and label-specific
fragility. The artifact includes transformed
CodeXGLUE, Big-Vul, and DiverseVul samples; exact public VulBERTa and LineVul
predictions on the full transformed CodeXGLUE test set; exact public
GraphCodeBERT-Devign predictions on a 512-origin transformed subset; an
official ReGVD graph run on the full transformed CodeXGLUE test set; a
non-collapsed AST-structural baseline; supporting detector-family baselines; a 512-origin composition and
identifier-ablation diagnostic; enhanced aggregation and flip-mechanism
analyses; and audit materials for checking transformation validity.

The results show that robustness cannot be inferred from clean benchmark
performance alone. On the full transformed CodeXGLUE test set, exact public
VulBERTa exhibits a measurable 7.01\% prediction flip rate and a clean-to-
variant F1 drop from 0.577 to 0.555. Exact public LineVul has a lower flip rate
of 1.22\%, but this apparent stability is limited by near-zero vulnerable
recall. Official ReGVD also illustrates the importance of calibration: its
fixed threshold collapses, whereas validation-threshold calibration produces a
non-collapsed full-test structural row with a 0.81\% flip rate but weak
balanced accuracy. Across
transformation families, identifier renaming, comment insertion, dead-branch
insertion, and safe dead-code carriers are more disruptive than layout-only
changes.

The practical implication is that robustness evaluation should become part of
the standard reporting and quality-assurance package for vulnerability
detectors. Researchers can use transformation tests to expose sensitivity to
superficial source features; benchmark designers can report transformed
variants alongside clean test sets; and tool builders can use paired
robustness tests as pre-deployment checks for learning-based security tools in
code-review and CI pipelines. Simple aggregation over transformed variants is
only a baseline; calibrated score averaging and selective abstention are more
informative diagnostics, but practical deployment still requires validation-set
calibration, better model design, training data, and semantic reasoning.

Overall, the strongest empirical claim is deliberately scoped to
CodeXGLUE/Devign, where exact public checkpoints are evaluated on the full
transformed test set and the semantic audit validates a randomly sampled
subset with strong annotator agreement, no invalid examples, a 95\% upper
bound of 0.43\% on the invalid rate, and conservative exclusions. Big-Vul and DiverseVul
strengthen external validity only in a limited sense: they show that the
transformations can be applied to additional vulnerability corpora and
demonstrate the need for imbalance-aware metrics. The 512-origin composition
probe suggests that composed edits can still produce measurable flips, but the
full-test exact-checkpoint claims remain single-transformation claims. This
distinction keeps the conclusions useful while avoiding overstatement from
sampled, supporting baselines.
